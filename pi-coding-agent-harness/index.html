Anatomy of a Coding Agent Harness

An LLM can write code. It cannot read your files, run your tests, or remember what it did five minutes ago. The harness is everything that turns a text predictor into an agent — and almost none of it is the model. A complete dissection of Pi, line by line.

Strip a coding agent down to its core and you find a loop so small it fits on an index card: send the conversation to a model, read its reply, if it asked to run a tool then run it, append the result, and send the whole thing back. Repeat until the model stops asking for tools. That loop is maybe forty lines of code.

Everything else — and there is a lot of everything else — exists to make that loop survive contact with reality. Reality is that there are nine different LLM wire formats and they disagree about everything. Reality is that conversations grow past the context window. Reality is that tools fail, time out, and spawn child processes that refuse to die. Reality is that the user wants to interrupt mid-task, branch the conversation, resume it tomorrow, and watch a diff render in their terminal at sixty frames a second. The harness is the name for all of that machinery.

This piece dissects Pi, an open-source, MIT-licensed coding agent by earendil-works, read in full — not skimmed. Pi is an unusually clean specimen: a TypeScript monorepo of four packages with sharp boundaries, extensive design docs written for its own agent to read, and no framework magic hiding the moving parts. We will build the mental model bottom-up, quoting the actual source at every step. By the end you should be able to re-derive the architecture yourself, and recognize the same bones inside Claude Code, Codex, Cursor, or whatever you build next.

How to read this

01 — The Mental Model

What a Coding Agent Harness Actually Is

Start with the smallest true thing. A large language model is a function: text in, text out. It has no memory between calls, no ability to act on the world, and no concept of "files" or "your repository" beyond what appears in its input. Give it a coding task and it will happily emit code — but it is guessing into the void, unable to check whether the file it is editing even exists.

An agent is what you get when you close the loop: you let the model request actions, you execute those actions in the real world, and you feed the results back. The model says "read config.ts"; you read it and hand back the contents; now the model is no longer guessing. The mechanism that lets a model request actions is tool calling — the model emits a structured request ({name: "read", arguments: {path: "config.ts"}}) instead of prose, and the harness fulfills it.

Figure 1 — The core agentic loop
The entire premise. The harness owns every box except the model. The dashed arrow — feeding tool results back and re-invoking the model — is the "agentic" part. Everything in later chapters is detail hung on this skeleton.

The loop is small; the harness is large

Here is the loop in pseudocode, which is genuinely close to what Pi runs:

the agentic loop, conceptuallypseudo
while (true) {
  const reply = await model.stream(systemPrompt, messages, tools)  // one LLM call = one "turn"
  messages.push(reply)
  const toolCalls = reply.content.filter(c => c.type === "toolCall")
  if (toolCalls.length === 0) break                       // model is done → exit
  for (const call of toolCalls) {
    const result = await runTool(call.name, call.arguments) // act on the world
    messages.push({ role: "toolResult", toolCallId: call.id, ...result })
  }
}                                                       // loop: model now sees the results

That is the whole idea. So why does Pi weigh in at four packages and tens of thousands of lines? Because each line of that pseudocode hides a swamp:

  • model.stream(...) — which model? Anthropic, OpenAI, Google, and a dozen OpenAI-compatible clones each have different request shapes, streaming formats, tool-call encodings, reasoning parameters, and authentication. Chapter 2.
  • messages.push(reply) — messages must be persisted so you can resume tomorrow, branched so you can explore alternatives, and compacted when they outgrow the context window. Chapters 6 & 7.
  • runTool(...) — the tool might be bash spawning a process tree, or edit doing a surgical string replacement that must not race a concurrent write. Output might be 40 MB. Chapter 8.
  • The loop itself must be interruptible (the user wants to steer), observable (the UI must render streaming tokens), and extensible (third parties add tools and hooks). Chapters 3–5, 10–11.

The art of harness design is drawing boundaries so that each swamp is drained in isolation. Pi draws them as four packages.

Three data types do most of the work

Before any code, internalize the three types that flow through the whole system. Almost every chapter is about transforming between them.

Message (pi-ai)
What the model understands. Exactly three roles: user, assistant, toolResult. Plain JSON, fully serializable. The lingua franca of every provider.
AgentMessage (agent-core)
A superset: every Message plus app-specific types (a bash-execution record, a UI notification, a compaction summary). The transcript is made of these.
SessionTreeEntry (agent-core)
What gets written to disk. A node in the conversation tree: a message, a model change, a compaction, a branch summary, a leaf pointer. Append-only.

The pipeline, which the rest of this piece elaborates, is: the session tree is read into AgentMessage[]; an optional transform prunes or injects; then a function called convertToLlm filters that down to the Message[] the provider layer accepts; the provider maps that to its wire format. Four representations, each earning its place. Keep this chain in mind:

The thesis

A coding agent is 5% model, 95% harness. The model is a stateless function you rent by the token. The harness is the operating system around it: it manages memory (context), I/O (tools), persistence (sessions), concurrency (the loop), drivers (providers), and the user interface. Judging an agent by its model is like judging a computer by its CPU. Pi is worth studying because it makes the other 95% legible.

02 — The Foundation

The Provider Layer: One API for Nine Wire Formats

The bottom layer, pi-ai, exists to tell one lie convincingly: that there is a single kind of language model. There is not. There is Anthropic's Messages API, OpenAI's two different APIs (the older Completions and the newer Responses), Google's Gemini, Amazon Bedrock, and a long tail of OpenAI-compatible providers (xAI, Groq, DeepSeek, Together, Cerebras, OpenRouter, Mistral, Moonshot, …) that are compatible right up until they aren't. They disagree on request shape, streaming format, how tool calls are encoded, how "thinking" is represented, how prompts are cached, and how you authenticate. pi-ai absorbs all of it behind one function.

The unified type model: plain serializable data

The design decision that makes everything else possible: the canonical types are plain JSON, no classes, no methods. A whole conversation round-trips through JSON.stringify. Here is the spine, from packages/ai/src/types.ts:

packages/ai/src/types.tstypescript
export interface UserMessage {
  role: "user";
  content: string | (TextContent | ImageContent)[];
  timestamp: number;
}
export interface AssistantMessage {
  role: "assistant";
  content: (TextContent | ThinkingContent | ToolCall)[]; // heterogeneous blocks
  api: Api; provider: Provider; model: string;     // SELF-DESCRIBING
  usage: Usage; stopReason: StopReason; errorMessage?: string;
  timestamp: number;
}
export interface ToolResultMessage<TDetails = any> {
  role: "toolResult";
  toolCallId: string; toolName: string;
  content: (TextContent | ImageContent)[];  // text AND images back to the model
  isError: boolean; timestamp: number;
}
export type Message = UserMessage | AssistantMessage | ToolResultMessage;

Two choices here pay off for the rest of the system. First, the assistant message is self-describing: it records the api, provider, and model that produced it. That single fact is what makes cross-provider handoff possible — when you replay a transcript to a different model, the layer can tell "this was me" from "this was a foreign model" and handle reasoning blocks accordingly. Second, a tool call is just a ToolCall block inside the assistant's content array, and its result is a separate toolResult message keyed by toolCallId. This representation is provider-neutral; each provider maps it to its own native shape (Anthropic tool_use/tool_result, OpenAI function_call/function_call_output, Google functionCall/functionResponse).

Token accounting rides along on every assistant message. Usage tracks input, output, cacheRead, cacheWrite (with a separate cacheWrite1h for Anthropic's 1-hour cache, billed at 2×), plus a computed cost breakdown in dollars. The harness reads these numbers to decide when to compact (Chapter 7) and to render the footer (Chapter 11).

Streaming: errors are values, not exceptions

The single most important abstraction in pi-ai is EventStream — a push/pull bridge that decouples the provider's network read-loop from the consumer's iteration. A provider pushes events as they arrive off the wire; a consumer either for awaits them or just awaits a final .result(). The same object is both an async-iterable and a promise.

packages/ai/src/utils/event-stream.tstypescript
export class EventStream<T, R = T> implements AsyncIterable<T> {
  private queue: T[] = [];
  private waiting: ((v: IteratorResult<T>) => void)[] = [];
  private finalResultPromise: Promise<R>;

  push(event: T): void {
    if (this.isComplete(event)) {              // terminal event…
      this.resolveFinalResult(this.extractResult(event)); // …resolves result()
    }
    const waiter = this.waiting.shift();
    if (waiter) waiter({ value: event, done: false }); // hand to a pending consumer
    else this.queue.push(event);                  // or buffer it
  }
  result(): Promise<R> { return this.finalResultPromise; }
}

The concrete subclass, AssistantMessageEventStream, sets the terminal condition to a done or error event and extracts the final AssistantMessage. This yields two superpowers. (1) complete() is literally stream().result() — non-streaming is a free special case of streaming. (2) Failures never throw out of the stream function. A network error, a timeout, an abort — all become a terminal error event carrying a fully-formed AssistantMessage with stopReason: "error" | "aborted", partial content, and partial usage. The agent loop above never needs a try/catch around the model call; it just checks stopReason. This "errors as values" contract is written into the type:

packages/agent/src/types.ts — the StreamFn contracttypescript
/**
 * Contract:
 * - Must not throw or return a rejected promise for request/model/runtime failures.
 * - Must return an AssistantMessageEventStream.
 * - Failures must be encoded in the returned stream via protocol events and a
 *   final AssistantMessage with stopReason "error" or "aborted" and errorMessage.
 */
export type StreamFn = (...args: Parameters<typeof streamSimple>) => ReturnType<typeof streamSimple>;

The event protocol itself is a tagged union: start, then deltas (text_delta, thinking_delta, toolcall_delta, each with a contentIndex tying it to a block), then done or error. Every event after start carries partial — the same message object being assembled in place — so a UI can read the full accumulated message at any moment. Blocks can interleave (a thinking delta, then a text delta, then back), so consumers key off contentIndex rather than assuming order.

Two tiers of options: native vs. simple

There are two entry points, and the split is the central abstraction seam of the package. stream() / complete() take provider-native options (e.g. Anthropic's thinkingEnabled). streamSimple() / completeSimple() take a unified SimpleStreamOptions whose one reasoning knob is reasoning: ThinkingLevel — an enum of "off" | "minimal" | "low" | "medium" | "high" | "xhigh". The agent loop only ever calls streamSimple; each provider maps that single level into its idiosyncratic thinking parameters. That is why agent-core code is provider-agnostic.

The hardest problem: cross-provider message replay

Every provider funnels the canonical Message[] through one shared function, transformMessages (packages/ai/src/providers/transform-messages.ts), before emitting its wire format. This is where the worst correctness bugs are concentrated — and centralized so they're solved once. It does five things: (1) downgrades images to text placeholders if the model lacks vision; (2) decides per assistant message whether it is the same model or a foreign one; (3) handles thinking blocks accordingly; (4) normalizes tool-call IDs (and rewrites the matching results); (5) synthesizes results for orphaned tool calls and drops errored turns.

transform-messages.ts — the same-vs-foreign thinking ruletypescript
const isSameModel =
  assistantMsg.provider === model.provider &&
  assistantMsg.api === model.api &&
  assistantMsg.model === model.id;

if (block.type === "thinking") {
  if (block.redacted) return isSameModel ? block : [];   // drop foreign redacted
  if (isSameModel && block.thinkingSignature) return block; // keep signed (even if empty)
  if (!block.thinking?.trim()) return [];                // drop empty
  if (isSameModel) return block;
  return { type: "text", text: block.thinking };          // foreign → plain text
}

So Claude's cryptographically-signed thinking is preserved verbatim when replayed to the same Claude model, but degraded to ordinary text when you hand the conversation to GPT or Gemini — which would otherwise reject the unrecognized signature. The orphaned-tool-call pass is equally pragmatic: any tool call lacking a result gets a synthetic "No result provided" error injected, because most APIs reject an unpaired tool call outright.

Lazy registration and the bundle-size story

Two registries hold the system together. A model registry (built from an auto-generated 450 KB table of model metadata) answers getModel("anthropic", "claude-sonnet-4-6") with a fully-typed Model object that knows its own API. An API-provider registry maps each API to its {stream, streamSimple} functions. Dispatch is trivial: stream() reads model.api and looks up the transport.

Crucially, providers register lazily. At import, each built-in API registers a thin wrapper whose real implementation sits behind a dynamic import(). The first call to a provider triggers a one-time load of that provider's SDK; until then it costs nothing. Combined with a /base entry point that skips built-in registration entirely, a browser bundle can include only the providers it actually uses — never pulling in, say, the AWS Bedrock SDK it will never call.

Also in this layer

Tool-schema validation with TypeBox: tool parameters are TypeBox schemas; arguments are coerced and validated with a cached compiled validator, and validation failures become a readable error string fed back to the model so it can retry. Prompt caching: Anthropic cache breakpoints land on the system prompt, the last tool definition, and the last message; OpenAI uses a prompt_cache_key derived from the session ID. OAuth: device-code and PKCE flows for Anthropic, OpenAI Codex, and GitHub Copilot, with token refresh. Overflow detection: ~22 regexes recognize "context too long" errors across providers so the harness can react. Each is a small, well-isolated module — the layer is broad but shallow.

With the foundation in place — a single streamSimple(model, context, options) that never throws and speaks every dialect — we can build the loop that calls it.

03 — The Beating Heart

The Agent Loop

We have a model abstraction that never throws. Now the loop. In Pi this is packages/agent/src/agent-loop.ts — a single file, a few hundred lines, and the densest, most important code in the whole project. Everything above it (the stateful Agent, the AgentHarness, the CLI) is a progressively richer wrapper around this function. Read it once and the rest is commentary.

AgentMessage vs Message: the two transcripts

The loop works in AgentMessage, not the provider's Message. Why a second type? Because a coding agent's transcript contains things the model must never see in raw form — a UI-only notification, a record of a user-run bash command, a compaction summary marker. AgentMessage is the union of real LLM messages plus app-defined custom messages, extended through TypeScript declaration merging:

packages/agent/src/types.tstypescript
export interface CustomAgentMessages {} // apps augment this via declaration merging

export type AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages];

// e.g. the coding agent adds, in packages/agent/src/harness/messages.ts:
declare module "../types.ts" {
  interface CustomAgentMessages {
    bashExecution: BashExecutionMessage;     // a user-run `!cmd`
    custom: CustomMessage;                   // extension-emitted
    branchSummary: BranchSummaryMessage;     // from tree navigation
    compactionSummary: CompactionSummaryMessage; // from compaction
  }
}

The bridge from the rich transcript to the model's three roles is one required callback, convertToLlm. It runs immediately before every model call and is where custom messages are either translated to a user message or filtered out entirely. A second, optional callback, transformContext, runs before that and operates at the AgentMessage level — this is the hook for pruning, compaction, and context injection. The full pipeline:

context.messages: AgentMessage[]
        │
        ▼  transformContext(messages)   — optional: prune / inject / compact (AgentMessage → AgentMessage)
        ▼  convertToLlm(messages)       — required: filter UI-only, translate custom (AgentMessage → Message)
        ▼  streamSimple(model, ctx)     — Message → provider wire format
   AssistantMessage

The loop, annotated

Here is the actual core, runLoop, lightly condensed. Notice it is two nested loops: an inner loop that runs turns while there are tool calls or pending steering messages, and an outer loop that restarts when follow-up messages arrive after the agent would otherwise stop.

packages/agent/src/agent-loop.ts — runLoop (condensed)typescript
let pendingMessages = (await config.getSteeringMessages?.()) || [];

while (true) {                              // OUTER: re-enters for follow-ups
  let hasMoreToolCalls = true;
  while (hasMoreToolCalls || pendingMessages.length > 0) { // INNER: one turn per iteration
    await emit({ type: "turn_start" });

    for (const message of pendingMessages) {     // inject steering before the model speaks
      await emit({ type: "message_start", message });
      await emit({ type: "message_end", message });
      currentContext.messages.push(message); newMessages.push(message);
    }
    pendingMessages = [];

    const message = await streamAssistantResponse(currentContext, config, signal, emit, streamFn);
    newMessages.push(message);

    if (message.stopReason === "error" || message.stopReason === "aborted") {
      await emit({ type: "turn_end", message, toolResults: [] });
      await emit({ type: "agent_end", messages: newMessages });
      return;                                // errors-as-values: no throw, just stop
    }

    const toolCalls = message.content.filter(c => c.type === "toolCall");
    const toolResults = [];
    hasMoreToolCalls = false;
    if (toolCalls.length > 0) {
      const batch = await executeToolCalls(currentContext, message, config, signal, emit);
      toolResults.push(...batch.messages);
      hasMoreToolCalls = !batch.terminate;       // tools can request early stop
      for (const r of toolResults) { currentContext.messages.push(r); newMessages.push(r); }
    }
    await emit({ type: "turn_end", message, toolResults });

    const snap = await config.prepareNextTurn?.({ message, toolResults, context: currentContext, newMessages });
    if (snap) { /* swap in fresh context / model / thinking for next turn */ }

    if (await config.shouldStopAfterTurn?.({ ... })) {     // graceful stop hook (e.g. compact)
      await emit({ type: "agent_end", messages: newMessages }); return;
    }
    pendingMessages = (await config.getSteeringMessages?.()) || [];
  }
  const followUps = (await config.getFollowUpMessages?.()) || [];
  if (followUps.length > 0) { pendingMessages = followUps; continue; } // outer loop re-enters
  break;
}
await emit({ type: "agent_end", messages: newMessages });

Five things to extract from this:

  • A "turn" is one model call plus its tool executions. The loop continues turning as long as the model keeps requesting tools. When a turn produces no tool calls and the queues are empty, the loop ends.
  • Everything is an event. The loop never touches a UI or a file directly; it emits a stream of typed events (turn_start, message_start/update/end, tool_execution_start/update/end, turn_end, agent_end). Whoever drives the loop reduces those events into state and renders them. This is the seam that lets the same loop power a TUI, an SDK, and an RPC server.
  • Errors stop the loop, they don't crash it. A failed model call arrives as an AssistantMessage with stopReason: "error"; the loop emits the closing events and returns cleanly. No exception ever escapes.
  • Steering and follow-up are queue-drain points. Steering messages are injected at the top of each inner iteration (interrupting between turns); follow-ups are checked only when the agent would otherwise stop (re-entering the outer loop). getSteeringMessages/getFollowUpMessages are callbacks, so the queue lives in the layer above.
  • prepareNextTurn is the hook the orchestrator uses to swap state mid-run. Between turns, the harness can hand back a fresh context, a different model, or a new thinking level — without ever mutating the request that is currently in flight. This is the mechanism behind "change the model mid-conversation and have it take effect next turn" (Chapter 5).

Tool execution: preflight, run, finalize

Tool execution is more subtle than "call the function". Each call passes through three phases — prepareToolCall (find the tool, coerce + validate arguments against its TypeBox schema, run the beforeToolCall gate which may block it), executePreparedToolCall (run tool.execute, forwarding streamed onUpdate partials as events), and finalizeExecutedToolCall (run the afterToolCall hook, which can patch the result or set terminate). Critically, a thrown error inside a tool is caught and converted into a tool result with isError: true — the model sees the error text and can retry, rather than the whole loop dying.

agent-loop.ts — error becomes a value the model can readtypescript
try {
  const result = await prepared.tool.execute(id, args, signal, onUpdate);
  return { result, isError: false };
} catch (error) {
  return { result: createErrorToolResult(error instanceof Error ? error.message : String(error)),
           isError: true };       // fed back to the LLM as a tool error
}

Batches of tool calls run in one of two modes. In parallel mode (the default), all calls are preflighted sequentially, then allowed tools execute concurrently via Promise.all; completion events fire as each tool finishes, but the persisted toolResult messages are re-ordered back into the assistant's original call order so the transcript stays deterministic. In sequential mode, calls run one at a time. A single tool can force the whole batch sequential by declaring executionMode: "sequential" — which the edit tool does, because two edits to overlapping regions in one batch must not race.

terminate

A tool can return terminate: true to hint that the agent should stop after this batch instead of doing another model call. The loop only honors it when every finalized result in the batch is terminating — a mixed batch continues normally. This is how a tool like "submit final answer" cleanly ends a run without a wasted follow-up turn.

04 — State & Lifecycle

The Stateful Agent

The raw agentLoop is a function: you hand it messages and config, it streams events, it returns. It holds no state between calls and gives you no way to interrupt it from outside. The Agent class (packages/agent/src/agent.ts) wraps it into a stateful, controllable object: it owns the running transcript, exposes lifecycle events to subscribers, manages the steering and follow-up queues, and defines what "the run is finished" precisely means.

State you can read, queues you can push to

agent.state exposes the live transcript and streaming status. Two of its fields use accessor properties that copy the array on assignment — a small but deliberate defense so that handing the agent a messages array doesn't let outside code mutate its internals by reference:

packages/agent/src/agent.ts — AgentState (shape)typescript
interface AgentState {
  systemPrompt: string;
  model: Model<any>;
  thinkingLevel: ThinkingLevel;
  tools: AgentTool[];                 // assigning copies the array
  messages: AgentMessage[];            // assigning copies the array
  readonly isStreaming: boolean;        // true until awaited agent_end listeners settle
  readonly streamingMessage?: AgentMessage;  // the partial being streamed right now
  readonly pendingToolCalls: ReadonlySet<string>;
  readonly errorMessage?: string;
}

Two FIFO queues sit beside the transcript. Steering messages interrupt the agent while it works ("stop, do this instead") — they're injected between turns. Follow-up messages wait until the agent would otherwise stop, then start a new turn ("also, when you're done, summarize"). Each queue has a mode: one-at-a-time (drain the oldest only) or all (drain everything at the next drain point). The loop's getSteeringMessages/getFollowUpMessages callbacks (Chapter 3) are wired straight to these queues.

The subtle part: when is a run actually "done"?

Naively, the run ends when agent_end is emitted. But subscribers (the UI, the session-saver) may do async work in response to agent_end — flushing to disk, final renders. If prompt() resolved before those finished, you'd have races. So the Agent defines settlement carefully: listeners are awaited in subscription order, and the run is idle only after the agent_end listeners have all settled.

agent.ts — every event is reduced into state, then awaited by listenerstypescript
private async processEvents(event: AgentEvent): Promise<void> {
  switch (event.type) {
    case "message_update": this._state.streamingMessage = event.message; break;
    case "message_end":    this._state.messages.push(event.message); break;
    case "tool_execution_start": /* add to pendingToolCalls */ break;
    case "agent_end":      this._state.streamingMessage = undefined; break;
  }
  const signal = this.activeRun?.abortController.signal;
  for (const listener of this.listeners) {
    await listener(event, signal!);   // awaited, in registration order — part of settlement
  }
}

The class is the lifecycle owner. prompt(input, images?) normalizes input into a user message and starts a run; it throws if one is already active (you must steer or followUp instead). continue() resumes from the current transcript without a new message — used for retries, with the rule that the last message must be a user or toolResult, never assistant. abort() signals the active run's AbortController. waitForIdle() returns the run promise. A failed run doesn't reject prompt() — it synthesizes a failure AssistantMessage and emits the normal closing event sequence, so the UI renders the error exactly like any other message.

Why two layers (loop vs. Agent)?

The raw loop is a pure, testable async generator of events with no hidden state — ideal for unit tests and for embedding. The Agent adds exactly the stateful concerns a real application needs: a persistent transcript, interruptibility, queueing, and deterministic settlement. Keeping them separate means the hard concurrency logic (settlement, abort) lives in one place and the loop stays trivial to reason about. The next layer, AgentHarness, adds a third ring: persistence and runtime reconfiguration.

05 — Orchestration

The Orchestrator: AgentHarness

The Agent can run a conversation in memory. A real coding agent must also persist every message to disk as it happens, let you change the model or tools mid-run without corrupting the request in flight, expose typed hooks so extensions can intercept tool calls and provider payloads, and do structural operations like compaction and branching. That is the AgentHarness (packages/agent/src/harness/agent-harness.ts) — the orchestration layer, and the most carefully-engineered file in the repo. Its own design doc states the goal bluntly: hooks and listeners must be able to call back into the harness "without corrupting in-flight turn snapshots, reordering persisted transcript entries, losing pending writes, or deadlocking settlement."

Phases: a state machine that rejects nonsense

The harness has an explicit phase, and structural operations assert idleness synchronously, before the first await:

packages/agent/src/harness/types.ts & agent-harness.tstypescript
type AgentHarnessPhase = "idle" | "turn" | "compaction" | "branch_summary" | "retry";

async prompt(text: string, options?): Promise<AssistantMessage> {
  if (this.phase !== "idle") throw new AgentHarnessError("busy", "AgentHarness is busy");
  this.phase = "turn";                       // set before any await — no race window
  const finishRunPromise = this.startRunPromise();
  try {
    const turnState = await this.createTurnState();
    return await this.executeTurn(turnState, text, options);
  } catch (error) { this.phase = "idle"; throw normalizeHarnessError(error, "unknown"); }
  finally { finishRunPromise(); }
}

Structural operations (prompt, skill, promptFromTemplate, compact, navigateTree) require idle and flip the phase atomically. Operations that are meant to run during a turn (steer, followUp, nextTurn, abort, and all the runtime config setters) are allowed while busy. Trying to start a second structural operation while busy throws a typed "busy" error rather than corrupting state.

Turn snapshots: config changes never mutate the request in flight

This is the central idea. The harness separates live config (the latest model, tools, resources, stream options you've set) from a turn snapshot (the frozen state used for one specific model call). When a turn starts, createTurnState() takes a snapshot. Setters like setModel() update live config immediately — but the running turn keeps using its snapshot. The change takes effect at the next save point.

Figure 3 — Live config vs. turn snapshot
A provider request only ever reads a snapshot. Changing the model mid-turn is safe: the in-flight request finishes on the old model, and the next turn's snapshot picks up the new one. This is what makes "switch model and keep going" not a data race.

The save point is where the magic happens. It is the harness's implementation of the loop's prepareNextTurn hook from Chapter 3:

agent-harness.ts — the save point (prepareNextTurn)typescript
prepareNextTurn: async () => {
  await this.flushPendingSessionWrites();        // 1. durably persist anything queued during the turn
  const nextTurnState = await this.createTurnState(); // 2. take a FRESH snapshot (new model/tools/context)
  setTurnState(nextTurnState);
  return { context: this.createContext(nextTurnState),
           model: nextTurnState.model, thinkingLevel: nextTurnState.thinkingLevel };

Pending writes: durable ordering under concurrency

Persistence is append-only and order-sensitive (Chapter 6). But config changes and extension writes can happen while a turn is running. If the harness wrote them immediately, they'd interleave incorrectly with the agent's own message writes. The solution: when busy, writes are queued as PendingSessionWrites and flushed in deterministic order at save points, at settlement, and in failure cleanup. When idle, they persist immediately. Every setter follows the same pattern:

agent-harness.ts — setModel: persist now if idle, queue if busytypescript
async setModel(model: Model<any>): Promise<void> {
  if (this.phase === "idle") {
    await this.session.appendModelChange(model.provider, model.id);  // write now
  } else {
    this.pendingSessionWrites.push({ type: "model_change", provider: model.provider, modelId: model.id }); // queue
  }
  this.model = model;                          // live config updates either way
  await this.emitOwn({ type: "model_update", model, previousModel, source: "set" });
}

Hooks: the harness's control plane

The harness wraps the loop's plain callbacks with a typed hook system. The loop's transformContext becomes a context hook; beforeToolCall becomes a tool_call hook that can block; afterToolCall becomes a tool_result hook that can patch. It also adds provider-level hooks (before_provider_request to patch stream options, before_provider_payload to rewrite the raw request body, after_provider_response to read status/headers) and its own lifecycle events (save_point, settled, queue_update). The design (documented in hooks.md) is elegant: events carry their own result type as a phantom, so the type system knows which events may return a value:

packages/agent/docs/hooks.md — events carry their result typetypescript
interface HookEvent<TType extends string, TResult = void> {
  type: TType;
  readonly [HookResult]?: TResult;   // phantom — encodes the result type at the type level
}
// tool_call may return {block, reason}; message_end returns nothing — enforced by types
interface ToolCallEvent  extends HookEvent<"tool_call", { block?: boolean; reason?: string }> { ... }
interface MessageEndEvent extends HookEvent<"message_end"> { message: AgentMessage; }

Different hooks have different reduction semantics, and getting these right is most of the work: context and before_provider_payload are sequential transforms (each handler sees the previous one's output); tool_call is early-exit on block; tool_result is patch accumulation; session_before_compact is early-exit on cancel. The coding agent's extension system (Chapter 10) is built almost entirely on these hooks.

Toward durability

Pi's durable-harness.md sketches the endgame: because the session is already an append-only log of every state change (model, thinking, active tools, compactions, leaf moves), a crashed harness could be reconstructed by replaying the log. The plan adds durable entries for queues, pending writes, and operation boundaries, with a conservative recovery policy: unfinished turns are marked interrupted; unfinished tool calls are not retried unless the tool declares itself idempotent (external side effects may already have happened). It is a clear-eyed acknowledgment that provider streams aren't resumable, so recovery must restart from durable boundaries.

06 — Memory on Disk

Sessions & Persistence: An Append-Only Conversation Tree

An LLM has no memory. The harness must provide it — not just within a run, but across days, across crashes, and across branches of exploration. Pi's answer is a single, elegant data structure: the session is an append-only log of typed entries that forms a tree. Everything — messages, model changes, compactions, the current position — is an entry. Nothing is ever mutated or deleted. To "go back" you just point at an older node.

Everything is an entry

A session on disk is a JSONL file: one JSON object per line, appended as events happen. Each line is a SessionTreeEntry — a discriminated union. The base shape gives every entry an id, a parent pointer (the tree edge), and a timestamp:

packages/agent/src/harness/types.ts — the entry uniontypescript
interface SessionTreeEntryBase {
  type: string;
  id: string;
  parentId: string | null;   // the tree edge — null means root
  timestamp: string;
}

type SessionTreeEntry =
  | MessageEntry             // { message: AgentMessage }       — user/assistant/toolResult/custom
  | ModelChangeEntry         // { provider, modelId }           — model switched here
  | ThinkingLevelChangeEntry // { thinkingLevel }
  | ActiveToolsChangeEntry   // { activeToolNames }             — tool set changed here
  | CompactionEntry         // { summary, firstKeptEntryId, tokensBefore } — see ch.7
  | BranchSummaryEntry       // { fromId, summary }             — a branch we came back from
  | CustomEntry             // { customType, data }            — extension state, not sent to LLM
  | CustomMessageEntry       // { customType, content, display } — extension message
  | LabelEntry              // { targetId, label }             — a bookmark on a node
  | SessionInfoEntry        // { name }                        — session display name
  | LeafEntry;             // { targetId }                    — moves the "current position" pointer

This is the durability design from Chapter 5 made concrete. Notice that configuration changes are entries too. When you switch from Sonnet to Opus, that is a model_change entry on the current branch. This is what makes "resume the session exactly as it was" possible — and it is the foundation for the durable-recovery plan, because replaying the log reconstructs not just the conversation but the entire harness configuration at any point.

The tree, and the leaf pointer

Because each entry has a parentId, the entries form a tree, not a list. Most of the time it's a straight chain (each entry's parent is the previous one). But when you edit an earlier message or navigate back, new entries get appended with an older parentId — creating a branch. The "current position" is tracked by a special, durable leaf entry. Critically, the leaf pointer is itself an append-only entry, not an in-memory cursor:

agent-harness.ts design note & session.tstypescript
// from the harness lifecycle doc:
// "setLeafId() is not an in-memory-only cursor update; it appends a durable
//  entry whose targetId is the active tree leaf. Reopening storage must
//  reconstruct the current leaf from the latest persisted leaf-affecting entry."

async moveTo(entryId: string | null, summary?): Promise<string | undefined> {
  await this.storage.setLeafId(entryId);     // append a leaf entry → new current position
  if (!summary) return undefined;
  return this.appendTypedEntry({ type: "branch_summary", ... }); // optionally record where we came from
}
Figure 4 — The session as a tree
Editing message u2 doesn't delete a2; it appends u2' with the same parent as u2, then moves the leaf. The old branch survives on disk forever. The active conversation is always just the path from the current leaf back to the root.

From tree to context: buildContext()

So how does a tree become the flat AgentMessage[] the loop needs? You walk from the current leaf back to the root (getPathToRoot), then fold that path into context. This is buildSessionContext, and it does three jobs in one pass: replay config (the last model/thinking/tools entry on the path wins), then emit messages — with special handling for compaction.

packages/agent/src/harness/session/session.ts — buildSessionContext (condensed)typescript
export function buildSessionContext(pathEntries: SessionTreeEntry[]): SessionContext {
  let model = null, thinkingLevel = "off", activeToolNames = null, compaction = null;
  for (const entry of pathEntries) {           // last-write-wins for config
    if (entry.type === "model_change") model = { provider: entry.provider, modelId: entry.modelId };
    else if (entry.type === "message" && entry.message.role === "assistant")
      model = { provider: entry.message.provider, modelId: entry.message.model }; // infer from history
    else if (entry.type === "compaction") compaction = entry;
  }
  const messages = [];
  if (compaction) {
    messages.push(createCompactionSummaryMessage(compaction.summary, ...)); // summary replaces old history
    // then only entries from firstKeptEntryId onward are appended…
  } else {
    for (const entry of pathEntries) appendMessage(entry); // custom/branchSummary become user messages
  }
  return { messages, thinkingLevel, model, activeToolNames };
}

This single function is why resume "just works": open the file, read the leaf, walk to root, fold. The model that was active, the tools that were enabled, the compaction that happened — all reconstructed from the log. The harness's buildContext() calls exactly this before every turn (Chapter 5's createTurnState).

Storage is an interface

SessionStorage is abstract: appendEntry, getEntry, getPathToRoot, getLeafId/setLeafId, createEntryId. The coding agent ships a JSONL-file implementation (one file per session under ~/.pi) and an in-memory one for tests. Because the whole tree API is behind this interface, you could back sessions with SQLite or a remote store without touching a line of the agent loop. Forking a session, listing sessions, and deleting are a separate SessionRepo interface.

07 — Surviving the Window

Context Management & Compaction

Every model has a finite context window. A long coding session — reading files, running tests, accumulating tool output — will eventually fill it. When that happens you have three options: truncate (lose information), summarize (lossy but smart), or stop. Pi summarizes. Compaction replaces a long prefix of the conversation with a structured summary, keeping recent turns intact. This is the single most important technique for long-horizon agentic work, and Pi's implementation (packages/agent/src/harness/compaction/) is worth studying in detail.

Estimating how full the window is

You can't compact if you don't know you're close to the limit. Pi estimates context tokens cheaply, preferring real numbers when available: it finds the most recent assistant message with provider-reported usage, takes that as ground truth, and adds a character-based estimate for everything after it.

packages/agent/src/harness/compaction/compaction.tstypescript
// ground truth from the provider + cheap estimate for the tail
export function estimateContextTokens(messages: AgentMessage[]): ContextUsageEstimate {
  const usageInfo = getLastAssistantUsageInfo(messages);   // real tokens, last assistant turn
  if (!usageInfo) { /* fall back to pure char/4 estimate of everything */ }
  const usageTokens = calculateContextTokens(usageInfo.usage);
  let trailingTokens = 0;
  for (let i = usageInfo.index + 1; i < messages.length; i++)
    trailingTokens += estimateTokens(messages[i]);          // ~chars/4, images ≈ 4800 chars
  return { tokens: usageTokens + trailingTokens, ... };
}

export function shouldCompact(contextTokens, contextWindow, settings): boolean {
  return settings.enabled && contextTokens > contextWindow - settings.reserveTokens;
}
// DEFAULT_COMPACTION_SETTINGS = { reserveTokens: 16384, keepRecentTokens: 20000 }

The threshold is contextWindow − reserveTokens — it triggers before the window is full, leaving 16K tokens of headroom for the summarization call itself plus the next response. This connects back to the loop's shouldStopAfterTurn hook (Chapter 3): the harness checks fullness after each turn and can gracefully stop to compact before the next model call would overflow.

Choosing the cut point

You can't cut the conversation just anywhere. You must cut on a turn boundary — never between an assistant's tool call and its result, or the replayed transcript becomes invalid (an orphaned tool call). findCutPoint walks backward accumulating tokens until it has gathered ~keepRecentTokens (20K) worth of recent history, then snaps to the nearest valid cut point (a user message or other turn start), being careful never to split a tool-call/tool-result pair:

┌──────────────────── full conversation (path to leaf) ────────────────────┐
 u1  a1  [tools]  u2  a2  [tools]  u3  a3 ......... u17  a17  [tools]  u18  a18
 └──────────── summarize this ───────────┘     └──── keep recent (~20K tok) ────┘
                                          ▲ cut point: a user-message turn boundary

 after compaction →  [compaction summary]  u15  a15 ......... u18  a18

The summarization prompt

The summary is generated by a dedicated model call with a fixed system prompt and a structured output format. This format is the actual "memory" the agent carries forward, so its design matters enormously — it's optimized for an LLM to resume work, not for a human to read. Here is the real prompt, verbatim:

Two details reveal real-world experience. First, there is a separate UPDATE_SUMMARIZATION_PROMPT for when a previous summary already exists: it instructs the model to preserve all prior information and only fold in what's new (moving items from "In Progress" to "Done"). Compaction is incremental — you summarize a summary plus new turns, not the whole history again. Second, the result is stored as a CompactionEntry carrying firstKeptEntryId and a details payload listing the files read and modified in the compacted span — so file-operation context survives the summary even though the raw tool calls don't.

Branch summaries: the cousin of compaction

Compaction summarizes down a branch you're keeping. Branch summarization handles the other case: you leave a branch (navigate back to an earlier node) and want to carry forward what you learned on the abandoned path. When navigateTree moves the leaf, it can generate a branch_summary entry recording what happened on the branch you're leaving, which then appears as a synthetic user message ("The following is a summary of a branch this conversation came back from…"). Both are the same idea: lossy compression of conversation history into a structured artifact, triggered at a safe boundary, recorded as a durable session entry, and re-inflated into a synthetic message at context-build time. Because they're entries on the tree, they're permanent and resumable — reopen the session next week and the summary is right there in the reconstructed context. Both are also interceptable via hooks (session_before_compact, session_before_tree), so an extension can supply its own summary or cancel the operation entirely.

08 — Acting on the World

The Tools

Tools are how the model touches reality. Everything else in this piece is plumbing to get a tool call from the model and a result back; the tools themselves are where the agent reads your files and runs your commands. Pi (packages/coding-agent/src/core/tools/) ships exactly seven built-ins — read, bash, edit, write, grep, find, ls — and the default coding profile enables just four of them (read, bash, edit, write), letting bash subsume search and listing. The design lessons are concentrated in three of them: bash, edit, and the truncation strategy they share.

Two-tier tool definitions

Each built-in is authored as a rich ToolDefinition — carrying not just the schema and executor but UI renderers, a one-line promptSnippet for the system prompt, and promptGuidelines — then wrapped into the minimal AgentTool the loop consumes. The model only ever sees {name, description, parameters}; the runtime adds execute. Every tool's filesystem and process access is injected via a pluggable Operations object, so the whole toolset can be redirected to SSH or a container without touching tool logic.

bash: a fresh process every time

The most important fact about the bash tool is what it is not: it is not a persistent shell. Every call spawns a brand-new child process. There is no shared environment, no working-directory persistence between calls — if the model wants to cd and then run something, it must chain cd foo && cmd in one call. This is a deliberate simplicity-and-safety trade: no leaked state, no zombie shell, no ambiguity about what environment a command runs in.

tools/bash.ts — the description the model sees, and the spawntypescript
// Description (verbatim): "Execute a bash command in the current working directory.
// Returns stdout and stderr. Output is truncated to last 2000 lines or 50KB
// (whichever is hit first). If truncated, full output is saved to a temp file."

const child = spawn(shellConfig.shell, [...shellConfig.args, command], {
  cwd,
  detached: process.platform !== "win32",   // own process group → killable as a tree
  env: env ?? getShellEnv(),
  stdio: ["ignore", "pipe", "pipe"],
  windowsHide: true,
});

Spawning detached puts the child in its own process group. That is the key to clean cancellation: on abort or timeout, Pi calls killProcessTree(child.pid) — killing the whole group, so a command that spawned its own children (a test runner, a dev server) doesn't leave orphans behind. There is no default timeout; the model opts in per call.

Bounded memory, complete output: the truncation strategy

Tool output can be enormous — a build log, a giant file, a find /. Loading all of it into context is both expensive and useless. Pi's strategy, shared across tools via OutputAccumulator and the truncate primitives, is: bound what goes into context, but never lose data — spill the full stream to a temp file and tell the model where it is. Two limits apply, whichever hits first: 2000 lines or 50 KB.

command stdout/stderr (combined stream)
        │
        ▼ OutputAccumulator: keep a rolling tail in memory + running counters
        │
   exceeds 2000 lines or 50KB?
        ├─ no  → return full output
        └─ yes → open /tmp/pi-bash-<hex>.log, stream the FULL output there
                 return the truncated TAIL + footer:
                 [Showing lines 4001-5000 of 5000. Full output: /tmp/pi-bash-….log]

The direction of truncation differs by tool, and it's a thoughtful detail: read truncates the head (you want the start of a file, with a Use offset=2001 to continue hint), while bash truncates the tail (errors and final results land at the end of a log). Every truncation footer is actionable — it tells the model exactly how to get more: a continuation offset, a doubled limit, or the path to the spilled file it can then read or grep. The model is never left guessing whether output was cut.

edit: exact, unique, non-overlapping, multi-edit

The edit tool is a surgical string-replace, and its contract is strict — enforced, not just documented. The model supplies an array of {oldText, newText} pairs; each oldText must occur exactly once in the file, all matches are computed against the original file (not incrementally), and edits must not overlap. The verbatim guidance pushes the model toward correctness:

tools/edit.ts — the schema & guidelines (verbatim)typescript
// oldText: "Exact text for one targeted replacement. It must be unique in the
//           original file and must not overlap with any other edits[].oldText."
const editSchema = Type.Object({
  path: Type.String(...),
  edits: Type.Array(Type.Object({ oldText: Type.String(...), newText: Type.String(...) })),
}, { additionalProperties: false });

// promptGuidelines (verbatim):
// - "Use edit for precise changes (edits[].oldText must match exactly)"
// - "When changing multiple separate locations in one file, use one edit call
//    with multiple entries in edits[] instead of multiple edit calls"
// - "Keep edits[].oldText as small as possible while still being unique."

The execution is a masterclass in defensive engineering. It strips and restores BOM, detects and preserves the file's line ending (CRLF vs LF), but normalizes everything to LF for matching so the model never has to reason about encoding. If an exact match fails, it retries with a fuzzy normalization pass — NFKC Unicode normalization, smart quotes → straight quotes, Unicode dashes → hyphen, exotic spaces → regular space — because models frequently emit curly quotes and non-breaking spaces that don't byte-match the source. When fuzzy matching is needed, only the touched lines are rewritten; every untouched line keeps its original bytes. Failures produce precise, actionable error strings ("Found N occurrences… The text must be unique. Please provide more context") that the model can act on. The tool returns both a display diff and a unified patch, and it declares executionMode: "sequential" so a batch of edits can't race.

The file mutation queue: no lost updates

Both edit and write mutate files, and tool calls can run in parallel. Two operations on the same file could read-modify-write over each other. The fix is a per-file serialization queue, keyed by the canonical realpath so two symlinks to the same inode share a queue, while different files proceed concurrently:

tools/file-mutation-queue.ts (condensed)typescript
const fileMutationQueues = new Map<string, Promise<void>>();

export async function withFileMutationQueue<T>(filePath: string, fn: () => Promise<T>): Promise<T> {
  const key = await getMutationQueueKey(filePath);  // realpath() canonicalizes symlinks
  const currentQueue = fileMutationQueues.get(key) ?? Promise.resolve();
  // chain a fresh promise onto this file's queue; release the next waiter in finally
  await currentQueue;
  try { return await fn(); } finally { /* releaseNext(); cleanup tail */ }
}

This same withFileMutationQueue is exported from the SDK so that custom file-mutating tools (from extensions) interleave safely with the built-in edit/write. It's a small primitive with an outsized correctness payoff — and notably, the queue key is realpath-canonicalized so the protection survives symlinks and even cooperating parallel pi sessions in the same repo.

09 — Telling the Model Who It Is

System Prompt, Skills & Context Files

The model's behavior is steered almost entirely by the system prompt and the context you inject. A coding agent's prompt is not a static string — it is assembled per turn from the active tools, the project's instruction files, available skills, and the current environment. The governing principle throughout is progressive disclosure: keep the always-on prompt small, and load detail on demand.

Assembling the system prompt

buildSystemPrompt (packages/coding-agent/src/core/system-prompt.ts) composes the prompt from sections. The base identity establishes the agent, then the active tools are listed using their one-line snippets (not their full descriptions — those go to the model via the tools API separately), then deduped guidelines, then trailing context. The opening is verbatim:

system-prompt.ts — the default identity block (verbatim)text
You are an expert coding assistant operating inside pi, a coding agent
harness. You help users by reading files, executing commands, editing
code, and writing new files.

Available tools:
- read: Read file contents
- bash: Execute bash commands (ls, grep, find, etc.)
- edit: Make precise file edits with exact text replacement, including
        multiple disjoint edits in one call
- write: Create or overwrite files

In addition to the tools above, you may have access to other custom
tools depending on the project.

Guidelines:
<deduped per-tool guidelines + "Be concise" + "Show file paths clearly">

The assembly order of the trailing sections matters: <project_context> (instruction files), then <available_skills>, then always-last the current date and working directory. A project-local SYSTEM.md (only when the project is trusted) can replace the whole identity block; an APPEND_SYSTEM.md adds to it.

Context files: AGENTS.md / CLAUDE.md

Project-specific instructions live in AGENTS.md (or CLAUDE.md) files. Pi discovers them by walking from the working directory up to the filesystem root, collecting one file per directory, plus a global one from ~/.pi/agent. They are injected with a path attribute so the model knows their provenance, and ordered outermost-ancestor first so the most-local instructions (cwd) appear last and take precedence:

system-prompt.ts — context-file injectiontypescript
prompt += "\n\n<project_context>\n\nProject-specific instructions and guidelines:\n\n";
for (const { path: filePath, content } of contextFiles) {
  prompt += `<project_instructions path="${filePath}">\n${content}\n</project_instructions>\n\n`;
}
prompt += "</project_context>\n";

This repo's own AGENTS.md (Pi is self-hosting — it's developed using Pi) is a good example: terse rules about commit style, never running the full test suite, no any in TypeScript, and how to test the TUI under tmux. That file is read into every turn's system prompt when working in the repo.

Skills: capabilities loaded on demand

A skill is a folder containing a SKILL.md with YAML frontmatter and a Markdown body of instructions. Skills implement the Agent Skills standard. The crucial design choice: skills are not exposed as a tool. Only their name, description, and file location are injected into the system prompt; the full body is loaded on demand by the model using the ordinary read tool when a task matches the description. This is progressive disclosure at its purest — a hundred skills cost only their one-line descriptions in context until one is actually needed.

SKILL.md format + how it appears in the prompttext
# a skill is a directory with SKILL.md:
---
name: pdf-processing
description: Extract text and tables from PDF files. Use when the user
             provides a PDF or asks about PDF contents.
---
# PDF Processing
<full instructions, scripts, references — only read when needed>

# injected into the system prompt as just metadata:
<available_skills>
  <skill>
    <name>pdf-processing</name>
    <description>Extract text and tables from PDF files…</description>
    <location>/abs/path/to/pdf-processing/SKILL.md</location>
  </skill>

Skills are discovered from global (~/.pi/agent/skills/), project (.pi/skills/, only when trusted), and package locations. description is the only hard requirement — a skill without one is silently dropped, because the description is precisely what lets the model decide when to load it. Name collisions resolve first-wins by load order. The model can also be forced to load one via the /skill:name slash command, which reads the body and wraps it in a <skill> block. Prompt templates are the simpler cousin: Markdown snippets invoked as /name that expand inline into the user message with $1/$@ argument substitution.

Three flavors of "extra context", three injection strategies

Context files (AGENTS.md) are always in the prompt — they're cheap and universally relevant. Skills put only a one-line teaser in the prompt and load the body on demand — many of them, each potentially large. Prompt templates aren't in the system prompt at all — they expand into the user turn when explicitly invoked. The harness matches the injection strategy to the cost and relevance of each resource. That discipline — never spend context tokens you don't have to — is the same instinct behind output truncation (Ch.8) and compaction (Ch.7).

10 — A Self-Extensible Agent

Extensions & the Hook System

Pi describes itself as "self-extensible," and it means it: the docs tell the agent to read its own extension documentation and write extensions on request. An extension is a single TypeScript file with a default-exported factory; it is loaded at runtime (no build step) and given one object, pi: ExtensionAPI, through which it registers tools, commands, keyboard shortcuts, CLI flags, message renderers, model providers, and — most powerfully — event handlers that hook the agent loop.

examples/extensions/hello.ts — a complete extensiontypescript
import { Type } from "@earendil-works/pi-ai";

  },

  pi.registerTool(helloTool);   // that's it — the LLM can now call hello()
}

The hook surface

Beyond registration, extensions subscribe to ~30 event types via pi.on(...). These map onto the harness hooks from Chapter 5 plus coding-agent-specific events. The reduction semantics — what a handler's return value does — vary deliberately by event, and that variety is the heart of the system:

So a "plan mode" extension can intercept tool_call and block any mutating tool until the user approves; a "rules" extension can inject project conventions via before_agent_start; a redaction extension can scrub secrets in context. The capability surface is broad: registered tools get full TUI renderers (Chapter 11), providers can add entire OAuth flows, and a shared EventBus lets extensions talk to each other.

Loading, ordering, and isolation

Extensions are discovered one level deep from .pi/extensions/ (project, trust-gated), ~/.pi/agent/extensions/ (global), and configured package paths. They are loaded with jiti — TypeScript executed at runtime, no precompilation — with host packages served either from a statically-bundled set (in the Bun binary) or aliased to workspace builds (in Node). The factory is awaited, so async setup completes before the first event fires. Action methods (sendMessage, setModel) throw if called during loading — they only work once the runner binds the live session.

Two properties keep the system robust. Ordering is deterministic: extensions run in load order, handlers in registration order. Errors are isolated: every handler is wrapped so one extension throwing never crashes another or the agent loop — the error is reported through a listener and execution continues (the one exception being tool_call, where a throw fail-safe-blocks the tool). There is, deliberately, no sandbox: extensions run with full host privileges. The only gate is project trust — project-local extensions don't load until you trust the directory.

Security boundary

Extensions, project skills, and SYSTEM.md can all execute arbitrary code or steer the agent, so they are gated on project trust. Pi itself ships no sandbox — it runs with the launching user's permissions. The docs are explicit that real isolation means containerizing the whole process (a micro-VM, Docker, or a policy sandbox). The harness gives you the trust gate; the OS gives you the cage.

11 — Pixels From Strings

The Terminal UI: Differential Rendering From Scratch

The interactive experience — streaming markdown, live diffs, a spinner, inline images, an editor with autocomplete, all redrawing smoothly — runs on Pi's own terminal UI library, pi-tui (packages/tui). No ncurses, no React-for-terminal. It is built on one idea: components produce flat arrays of styled strings, and a diff engine writes the minimum bytes to turn the previous frame into the next.

A frame is string[], not a cell grid

The surprising core decision: there is no 2D character grid. A frame is just string[] — one fully-styled string per terminal row, ANSI escapes embedded inline. The component contract is correspondingly tiny:

packages/tui/src/tui.ts — the entire Component interfacetypescript
export interface Component {
  render(width: number): string[];   // the only required method; height = array length
  handleInput?(data: string): void;  // optional: focused input
  wantsKeyRelease?: boolean;
  invalidate(): void;             // drop cached render
}

The model is retained: you build a long-lived tree of components once and mutate them over time (the root TUI is a Container). Strings are trivially cacheable and comparable with ===, and components compose by array concatenation. The price you pay for skipping a cell grid is that every width calculation must be Unicode- and ANSI-aware — wide CJK chars count as 2, emoji as 2, zero-width marks as 0, escape codes as 0. That cost is paid once, in a width engine (visibleWidth, wrapTextWithAnsi, truncateToWidth) that every component reuses.

The diff: rewrite only what changed

On each render, the tree produces newLines; the engine compares it line-by-line against the previous frame and rewrites only the changed range. A spinner tick rewrites exactly one line. The whole frame is wrapped in synchronized-output markers (CSI 2026) and written in a single call, so the terminal paints it atomically — no flicker, no partial frames, minimal bytes (which matters over SSH).

tui.ts — the differential scan & atomic write (condensed)typescript
let firstChanged = -1, lastChanged = -1;
for (let i = 0; i < Math.max(newLines.length, this.previousLines.length); i++) {
  if ((this.previousLines[i] ?? "") !== (newLines[i] ?? "")) {
    if (firstChanged === -1) firstChanged = i;
    lastChanged = i;
  }
}
let buffer = "\x1b[?2026h";                  // begin synchronized output (atomic frame)
// …move cursor to firstChanged (relative moves), \x1b[2K + rewrite each changed line…
buffer += "\x1b[?2026l";                       // end synchronized output
this.terminal.write(buffer);                  // ONE write() for the whole frame

The engine keeps three strategies: a clean first paint, a full clear-and-redraw (when width changes, since wrapping changes, or content shifts above the viewport), and the normal differential update. Cursor motion is entirely relative, with the TUI maintaining its own model of where the hardware cursor is and where the viewport sits — which lets ordinary terminal scrollback keep the transcript history. One hard rule guards the whole scheme: a line wider than the terminal would corrupt the relative-cursor model, so the renderer treats it as a fatal bug, dumps a crash log, and throws rather than silently garbling the screen.

Input, the editor, and images

Input flows from raw stdin bytes through a StdinBuffer that splits batched reads into one complete escape sequence per event, then through a key parser that speaks the modern Kitty keyboard protocol when available (precise modifiers, key-release events) and falls back to modifyOtherKeys and legacy bytes — negotiated at startup with a clever Device-Attributes sentinel so there's no timeout. The multi-line editor stores text as logical lines with a row/col cursor, navigates by grapheme and by word (via Intl.Segmenter), supports an emacs-style kill-ring and a deep-clone undo stack, collapses large pastes into atomic [paste #1 +40 lines] markers, and drives a fuzzy-matched autocomplete popup for / commands and @ file references. Images render through the Kitty graphics or iTerm2 inline-image protocols when detected, falling back to a text placeholder under tmux.

How the chat UI wires up

The interactive mode (interactive-mode.ts) builds about eight long-lived containers once — header, chat transcript, status (the spinner), the editor, footer — then never diffs the transcript itself. Instead it subscribes to the agent's event stream and mutates components in place: message_start creates one AssistantMessageComponent; each message_update token feeds updateContent on that same component; each tool call gets a ToolExecutionComponent keyed by id. Every handler ends in ui.requestRender(), and the framework's only job is "tree → strings → minimal terminal writes." This is the same event-driven decoupling as everywhere else: the loop emits, the UI reduces and renders.

12 — Four Faces, One Engine

Modes: Interactive, Print, RPC, SDK

The same AgentSession drives four very different front-ends. This is the payoff of the strict layering: because the agent loop only emits events and the session exposes a clean method surface (prompt, steer, setModel, fork, compact…), you can wrap it in a terminal UI, a one-shot CLI, a JSON-RPC server, or an in-process library without changing the engine.

The boot decision

The CLI entry (cli.ts → main.ts) parses argv and collapses it into one of four modes. The decision is a small, legible function — and notably, piping into or out of pi auto-selects print mode, which is what makes pi -p "..." and shell pipelines work:

main.ts — resolveAppModetypescript
function resolveAppMode(parsed, stdinIsTTY, stdoutIsTTY): AppMode {
  if (parsed.mode === "rpc")  return "rpc";            // --mode rpc
  if (parsed.mode === "json") return "json";           // --mode json (print variant)
  if (parsed.print || !stdinIsTTY || !stdoutIsTTY) return "print"; // -p, or piped
  return "interactive";                                // the default
}

RPC: the session, serialized

RPC mode is the most revealing, because it shows that the whole agent is controllable through a narrow message protocol. It speaks strict newline-delimited JSON over stdio (deliberately hand-rolled, not Node's readline, because readline splits on Unicode line separators that are legal inside JSON strings). Every message is discriminated by a type field. Commands carry an optional id; responses echo it; events never carry an id — that's how the client demultiplexes the two streams flowing over the same pipe.

modes/rpc/rpc-types.ts — the command union (excerpt)typescript
type RpcCommand =
  | { id?: string; type: "prompt"; message: string; images?: ImageContent[];
      streamingBehavior?: "steer" | "followUp" }
  | { id?: string; type: "steer"; message: string }
  | { id?: string; type: "abort" }
  | { id?: string; type: "set_model"; provider: string; modelId: string }
  | { id?: string; type: "compact"; customInstructions?: string }
  | { id?: string; type: "fork"; entryId: string }
  | { id?: string; type: "get_state" } | ... ;   // ~30 commands, each ≈ one AgentSession method

The dispatcher is one big switch (command.type), each branch calling an AgentSession method — the same methods the in-process SDK exposes. So RPC is, almost literally, the session API serialized to JSON. The prompt command is special: it doesn't await the run; it acknowledges once preflight succeeds and then lets the result stream out as events, so a client can interleave a steer while the agent works. The other side, RpcClient, spawns pi --mode rpc as a subprocess and offers typed promise-returning methods over the same framing — the basis for embedding Pi from any language.

SDK: skip the subprocess

For Node/TypeScript callers there's a more direct path: createAgentSession(options) builds an AgentSession in-process. You pick the model, tools, resource loaders, and session storage, then drive the returned session directly — type-safe, no serialization. The interactive, print, and RPC modes are themselves just three consumers of this factory plus a thin AgentSessionRuntime that handles swapping the active session (new / switch / fork / clone). Same engine, four faces.

13 — What Makes It Hold Together

The Design Principles

We have walked the whole machine bottom to top. Step back and the same handful of principles recur at every layer — and they are what separate a harness that survives real use from a demo that falls over. If you take nothing else from this dissection, take these.

1. Errors are values, not exceptions

The provider layer's stream function is contractually forbidden from throwing; failures arrive as an AssistantMessage with stopReason: "error". A tool that throws is caught and converted to a tool result with isError: true. The result is that the agent loop has almost no error-handling code — it just checks stopReason and feeds tool errors back to the model, which can read them and retry. Failure becomes ordinary data flowing through the same path as success.

2. Decouple production from consumption

The EventStream separates a provider's network read-loop from whoever consumes it. The agent loop emits a typed event stream rather than calling a UI. The harness's save points let it await persistence and hooks without blocking the provider transport. This single pattern — producers push events, consumers pull at their own pace — is what lets one engine drive a TUI, an SDK, and an RPC server, and what keeps streaming smooth under backpressure.

3. Snapshot the volatile, never mutate in flight

A provider request reads only a frozen turn snapshot. Change the model, tools, or thinking level mid-run and the change lands at the next save point, never corrupting the request in flight. Compaction cuts only on turn boundaries. The file mutation queue serializes writes per file. Everywhere mutability meets concurrency, Pi inserts a boundary — a snapshot, a save point, a queue — so that "change it while it's running" is safe by construction rather than by luck.

4. Progressive disclosure of context

Context tokens are the scarcest resource, so the harness spends them grudgingly. Skills put a one-line teaser in the prompt and load the body on demand. Pi's own docs are referenced by path, not inlined. Large tool output is truncated with an actionable pointer to the full spill file. Long histories are compacted into structured summaries. The recurring instinct: keep the always-on footprint minimal, and load detail only when a task actually needs it.

5. Append-only state is resumable state

The session is a tree of immutable entries — messages and configuration changes and the current-position pointer. Nothing is mutated; branches are new edges; "undo" is moving a pointer. Because the entire history is a replayable log, resuming a session is just "walk from the leaf to the root and fold," and full crash recovery becomes a tractable design problem rather than a rewrite.

6. Draw boundaries you can defend with types

Four packages, dependencies strictly downward. The model is self-describing so cross-provider replay is decidable. Hook events carry their result type as a phantom so the compiler knows which may return a value. The compat flag type is keyed on the model's API so the wrong flags can't be set. Public failures are normalized to one error type with a stable code. The boundaries aren't just conventions — they're encoded so the type checker enforces them.

The whole machine, in one breath

A coding agent is a tiny loop wrapped in a large amount of careful engineering. pi-ai turns nine LLM dialects into one never-throwing streamSimple. The agent loop turns that into turns, executing tools and emitting events. The Agent adds a transcript, queues, and settlement; the AgentHarness adds phases, snapshots, durable writes, and hooks. Sessions make the conversation an append-only tree; compaction keeps it inside the window. Tools act on the world with bounded output and serialized mutations; the system prompt, skills, and context files tell the model who it is via progressive disclosure. Extensions hang new behavior off the hooks; pi-tui renders it all with a string-diff; and four modes expose the same session as a CLI, a pipe, a JSON stream, and an RPC server. None of it is the model. All of it is the harness.
